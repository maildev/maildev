MailDev has caught development email for over a decade with roughly the same
architecture underneath. 3.0 replaces all of it.

## What changed

**A complete TypeScript rewrite.** The project is now a pnpm monorepo of focused
packages — `@maildev/core`, `@maildev/smtp`, `@maildev/api`, `@maildev/ui`, and
`@maildev/mcp` — behind the same `maildev` CLI you already use. Types are
published, so [embedding MailDev](/docs/reference/node-api/) in a test suite is no
longer an exercise in guessing option shapes.

**A new inbox.** The web UI is a React application: searchable, keyboard-driven
via a command palette, with a
[responsive preview](/docs/web-ui/) that renders your HTML at phone and tablet
widths, and light and dark themes that follow your system setting.

**A Fastify API.** The [REST API](/docs/reference/rest-api/) gained pagination and
search on the listing endpoint, bulk delete, mark-all-read, and a health endpoint
that stays unauthenticated so container health checks keep working.

**Storage that survives a restart.** Point `--mail-directory` at a folder and mail
is persisted and restored on startup. `--max-emails` bounds the store and evicts
the oldest messages — and their files — once the limit is reached.

## The MCP server

The addition we are most interested in: MailDev 3.0 has a built-in
[Model Context Protocol server](/docs/ai/mcp/).

```console
maildev --mcp
```

That exposes five tools, three resources, and four prompts to any MCP client —
Claude Code, Claude Desktop, Cursor, Codex, Windsurf. Your coding agent can search
the inbox, read a message in full, pull an attachment, and delete mail to reset
state.

The reason this matters is narrower than "AI in the inbox". Email is the last leg
of a lot of flows an agent otherwise handles end to end: signup confirmation,
password reset, magic links, invitations. Without inbox access, the agent
implements the feature and stops, because verifying it requires a human to look at
a browser tab. With it, the agent triggers the flow, reads the message, follows
the link, and reports whether it worked.

In practice that turns into requests like:

> Clear the MailDev inbox, then register `alice@test.com` and confirm the
> verification link actually verifies her account.

The [Claude Code walkthrough](/docs/ai/claude-code/) has the full loop, including
the prompts that work and the ones that do not.

:::warn
The MCP server hands an agent the complete contents of every message MailDev
holds. That is the point, and it is also why MailDev belongs on your own machine
pointed at your own development inbox — never at anything holding real mail.
:::

## Upgrading from 2.x

The CLI is unchanged: every flag from 2.x still works, with the same names and
defaults. Two things to know:

- **Node.js 20 or newer is required.** MailDev 3.0 is ESM-only.
- **The programmatic API moved from callbacks to promises.** If you embed MailDev in a test suite, `start()` and `stop()` now return promises and the read methods are async. The [programmatic API reference](/docs/reference/node-api/) documents the migration.

```console
npm install -g maildev@latest
```

If 3.0 breaks something that worked, `npm install -g maildev@2` gets you back, and
[an issue](https://github.com/maildev/maildev/issues) is genuinely useful — the
rewrite is large and the edges are where reports help most.
